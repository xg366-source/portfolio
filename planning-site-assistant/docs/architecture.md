# 系统架构

```
规划文件 (.md/.pdf) ──► ingest.py 按章节分块（保留文件+章节）
                              │
                              ▼
                        BM25 索引 (retriever.py)
                              │
问题 ──► answer.py 路由 ──────┼──► 文档问答：检索 → 阈值检查 → 带引用回答
              │               │
              ├──► GIS 查询：排名/中位数/单 tract 画像/相关分析
              │         (gis_query.py，直接算图层属性，数字不经 LLM)
              │
              └──► 拒答：分数或词覆盖低于阈值 → 明确“没有足够依据”
                              │
                              ▼
              FastAPI /ask ──► web/index.html（Leaflet 地图 + 问答面板）
```

## 三个关键决策

1. **数字走结构化查询，不走检索/LLM。** “某 tract 占比多少、哪个最高”由代码对 GeoJSON 属性计算，引用到图层+GEOID。LLM 不负责算数。
2. **拒答是功能，不是失败。** 阈值（config.yaml 的 min_score / min_coverage）用评估集里的无答案题校准；误拒率与漏拒率同时报告。
3. **引用粒度到章节/要素，且引用必须属于真正产出该数字的图层。** 评估中曾出现排名答案引用了错误图层文件（字段来自合并属性表）——已用 FIELD_SOURCE 映射修复，并成为失败案例 #1。

## 方法护栏
- 每千人比率排名默认人口 ≥2,000、餐厅占比另要求餐厅数 ≥10，理由写在 data/docs/data_notes.md，回答中同步注明。
- 检索基线是 BM25（零 key 可复现）；换 embedding 后端时接口不变，用同一评估集对比——这是 v2 的计划实验。
