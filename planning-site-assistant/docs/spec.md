# 项目规格 + 评估方案 v1（仓库外原件同步）

> 定位：AI 产品经理 / AI 工程师方向的独立工程案例（新增作品，不是改现有 6 个建筑项目）
> 一句话：输入规划文件 + GIS 数据 → 可检索资料库 → 带引用的基地问答（无依据就拒答）→ 地图界面展示 → 用标准答案测试集量化评估
> 作者背景优势：建筑本科 + 康奈尔高级城市设计硕士 + 已有成套 GIS 数据清洗经验

## 一、为什么只新增这一个就够了（不要再开第二个）

现有作品集（27 页，6 个项目）的强项和缺口：

| 维度 | 现状 | 招聘方会问 |
|---|---|---|

| 产品 | 《AI 作品集点评助手》已有 PM 完整链路（访谈→PRD→原型→可用应用），但不在这本 PDF 里 | 投 AI PM 时要把它并进来 |

结论：
- **AI PM 线** = 《AI 作品集点评助手》（已有）+ 本项目（补技术可信度）
- **AI 工程师线** = 本项目（主力）+ 《AI 作品集点评助手》演示模式/代码（辅证）
- 不要再做 Midjourney/Stable Diffusion 出图类案例——那证明的是提示词，不是工程，招聘方已经看腻了。

现有项目只需“改口径”，不用重做：
1. **Conflux Strand**：抽 1 页改成“数据驱动需求研究”案例（数据源、分组方法、价值维度如何变成设计决策）。
2. **The Topology Engine**：抽 1 页改成“GIS 数据管线”案例（图层清单、清洗/叠加逻辑、结论如何导出）。正好和本项目同领域，互相印证。

## 二、MVP 范围（做这些，不做那些）

### 做（P0）
1. **资料库**：10–15 份文件封顶。PDF/文本规划文件 + 3–4 个 GIS 图层（GeoJSON）。
2. **检索问答**：回答必须带引用（文件名 + 页码/章节，或图层名 + 要素 ID）；检索分数低于阈值 → 明确拒答：“资料库中没有足够依据”。
3. **地图/网页界面**：左侧地图（点图层/地块高亮对应区域），右侧问答 + 引用列表。能点、能演示即可，不追求产品级打磨。
4. **评估集**：40 题（见第四节），跑出量化结果表，并根据结果至少做 **1 轮调优**（改分块大小 / 阈值 / 提示词），展示前后对比。
5. **公开交付物**：GitHub 仓库、架构图、90 秒演示视频、评估报告、失败案例页。

### 不做（写进 README 的“非目标”，反而显专业）
- 不做多用户/登录/权限；不做实时数据更新；不做微调模型（RAG 能解决就不用微调，要能说清这个取舍）；不追求覆盖整个城市，只做一个基地。

## 四、技术栈（按你现有技能定，不追新）

| 层 | 选型 | 理由 |
|---|---|---|
| 文档解析 | Python + PyMuPDF | PDF 按页拆，天然保留页码给引用用 |
| 分块/向量化 | LangChain 或 LlamaIndex 二选一 + Embedding API（或本地 bge） | 面试高频问答点，能讲清 chunk size / overlap 取舍 |
| 向量库 | Chroma（本地文件即可） | 零运维，仓库可复现 |
| GIS 处理 | GeoPandas + Shapely | 你 Canvas 作业正在学，正好一鱼两吃；空间问题走结构化查询，不让 LLM 猜数字 |
| 后端 | FastAPI，一个 `/ask` 接口 | 返回：答案 + 引用数组 + 检索分数 + 是否拒答 |
| 前端 | 单页 HTML/JS + Leaflet 地图 | 你熟 HTML/CSS/JS；Leaflet 加载 GeoJSON 最省事 |
| 模型 | 任一主流 LLM API（服务端调用，key 不进前端） | 与《作品集点评助手》同一条安全口径 |

**关键设计决策（面试必问，先想好答案）：**
1. 数字类问题（如“该 tract 西裔占比多少”）走 GIS 结构化查询，不走向量检索——LLM 不负责算数。
2. 拒答阈值不是拍脑袋：用评估集里的“无答案题”校准，报告里给出阈值选择依据。
3. 引用粒度到页/到要素，不做整文档引用——粒度太粗等于没引用。

## 五、评估方案（这个项目的灵魂，权重高于界面）

### 测试集：40 题，分布先定死再开发（防止“边做边凑题”）

| 类别 | 题数 | 测什么 | 例子（方案 A） |
|---|---|---|---|
| 文档事实题 | 14 | 检索相关 + 引用正确 | “该走廊所在社区的分区用途允许哪些商业类型？依据哪份文件第几页？” |
| GIS/空间题 | 8 | 结构化查询准确 | “311 投诉量最高的 tract 是哪个？主要投诉类型是什么？” |
| 跨源综合题 | 6 | 多文档/文档+图层拼接 | “人口西裔占比高的区域，餐厅检查 B 级以下占比也更高吗？” |
| 无答案题（拒答） | 8 | 无依据时是否拒答 | 问资料库里根本没有的城市/政策/数据 |
| 歧义/陷阱题 | 4 | 是否乱引、张冠李戴 | 名称相似的两个地块、过期口径的数据 |

每题标注：标准答案、应引用来源（文件+页/图层+ID）、类别。存成 `eval/questions.jsonl` 进仓库。

### 指标（报告里就这 5 个，不要堆更多）

1. **检索 Recall@5**：应引来源出现在前 5 条检索结果中的比例
2. **引用准确率**：答案的引用确实支撑该句结论的比例（人工按 0/1 核）
3. **答案正确率**：与标准答案比对，0/1/2 分制（错/部分对/全对）
4. **拒答准确率**：无答案题中正确拒答的比例；同时看有答案题被误拒的比例（过度拒答）
5. **幻觉率**：答案中出现资料库不存在的事实的题占比

### 流程
跑 v1 → 出结果表 → 挑最大的失败类 → 只改一个变量（分块/阈值/提示词）→ 跑 v2 → 前后对比表进作品集。
**这一轮迭代记录，比最终分数本身更值钱**——它证明你会用评估驱动开发，而不是凭感觉调。

## 六、失败案例页（单独成页，至少 3 个，写成这个格式）

每个案例四段：问题 → 系统原答（截图） → 错在哪（分类：检索未命中 / 引用张冠李戴 / 该拒未拒 / 过度拒答 / 空间概念混淆） → 怎么修的 / 为什么暂不修。
诚实标注未修的，比全是成功案例可信得多。

## 七、作品集呈现（4–6 页 + 仓库）

1. **问题与用户**：谁在查规划资料时痛（学生/年轻规划师跨几十份 PDF + GIS 找依据），现有做法多慢
2. **系统架构图**：数据管线 → 索引 → 检索 → 生成/拒答 → 地图界面，一张图讲完
3. **演示**：界面截图 + 地图高亮 + 引用卡片；附 90 秒视频二维码/链接
4. **评估报告**：测试集构成 + 5 指标 v1/v2 对比表
5. **失败案例**：见第六节
6. **取舍与反思**：为什么 RAG 不微调、为什么数字走结构化查询、下一步（权限/增量更新）

仓库 README 结构：Demo 链接 → 架构图 → 如何本地运行 → 数据来源与口径 → 评估方法与结果 → 失败案例 → 非目标。

## 九、面试自检（做完后能答出才算完成）

- 你的 chunk size 为什么是这个数？换大/换小评估怎么变？
- 拒答阈值怎么定的？误拒和漏拒你更怕哪个，为什么？
- 引用准确率怎么核的？谁核的？
- 如果资料互相矛盾，系统怎么办？（当前答案应诚实：未处理/仅提示双来源）
- 这套评估集的局限是什么？（题量小、自编题偏差——能主动说出即加分）
