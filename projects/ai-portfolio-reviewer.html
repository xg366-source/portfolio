案例 01 · AI 产品

AI 作品集点评助手

给作品集一个"有页码、有证据、敢说『不确定』"的第一轮自检——上传 PDF，返回最值得改的 Top3 处。

我的角色
独立完成（需求 → 前端 → 提示词 → 隐私方案）
技术栈
原生 HTML/CSS/JS + DeepSeek API
状态
原型可运行 · 演示模式免 Key

求职与留学申请的作品集，普遍卡在同一个环节：没人能给具体、可执行、可追溯的反馈。我把这件事做成一个能直接跑的产品原型。

背景与目标

作品集是设计类求职/申请中最重的交付物，但反馈链路极不透明：导师回复笼统、第三方付费点评贵且不可追溯。目标：做一个轻量工具，用户上传 PDF 后立刻拿到 带页码证据、具体改法、工作量估计与置信度 的 Top3 修改建议，并把"先改哪 3 处"讲清楚。

用户与问题

目标用户：即将投递作品集的设计类学生与求职者（建筑、城市设计方向为主）。

  • 导师/朋友反馈多为"整体不错、某某图可以更好"，没有页码、没有优先级、没有具体改法
  • 付费点评贵，且结论无法回看证据，不敢全信
  • 临近 DDL 时最需要的是"先改哪几处"，而不是整体评价或分数
洞察
  • 要的不是评分，是"行动清单"——所以产品不输出总分，只输出按优先级排序的 Top3，每条都标注页码、可回看的证据和改法
  • 对"AI 说教"天然不信任——所以每条建议带 evidence（对应原文场景）与 confidence（高 / 中等 / 无法充分判断），模型看不清就明说"不确定"，而不是硬编
  • 试用门槛决定留存——没有 Key 也要能体验完整流程，于是做演示模式
方案与取舍
  • 形态取舍：不做 Chrome 插件 / 小程序 / 后端服务，做纯前端单页——零后端、可托管在任何静态空间、分享成本最低、不依赖个人服务器
  • 隐私取舍：API Key 只存浏览器 localStorage；PDF 原文件留在本机，仅把压缩后的页面截图发往模型；历史报告只保留文字——用"本地优先"换用户信任
  • 模式取舍：无 Key 演示模式（内置示例报告）+ 有 Key 真机模式，把"先体验再接入"的成本降到最低
  • 提示词取舍：强制结构化输出（JSON：页码、优先级、类别、证据、改法、工作量、置信度、覆盖范围），并对"看不清、无法确认"显式要求标注 uncertain，减少幻觉
方法与数据

流程：上传 PDF → 本地渲染前 12 页 → 压缩为页面截图 → 按用途（院校申请 / 设计求职）选择评审标准 → 调 DeepSeek API → 解析结构化结果 → 渲染为带页码证据的报告。

两种评审模式各配独立提示词；报告含优先级 / 类别 / 置信度标签、工作量与可逆性标注、覆盖范围说明。

待补充：真实使用数据（体验人数、点评次数、试用→填写 Key 的转化率）。我目前没有可用数字，不编造。
结果

完成一个可运行的单页原型：演示模式无需任何配置即可体验完整点评流程；真机模式由用户浏览器直连 DeepSeek。包含历史报告记录、提交倒计时输入、院校申请/设计求职双模式、优先级与置信度标签、演示内容明确标注等细节。

我的角色与复盘

独立完成：需求定义、信息架构、前端实现、提示词设计、隐私与演示机制。全程没有用框架，把每一步走明白了。
