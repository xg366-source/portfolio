案例 02 · AI 工程

规划资料与场地分析助手

查基地资料不用再翻几十份 PDF：问答带引用、没依据就拒答、数字不让模型猜——而且效果用测试集说话，不凭感觉。

我的角色
独立完成（数据管线 → 检索/查询 → 评估）
技术栈
Python · BM25 检索 · GIS 结构化查询 · FastAPI · Leaflet
状态
本地可运行 · 代码已公开（见文末链接）

规划前期调研最耗时的不是分析，是找依据：政策在 PDF 里、数据在 GIS 图层里、口径在说明文档里。这个系统把三者接成一个能问、能查、能验的助手。

背景与目标

基地：纽约皇后区 Junction Blvd—Corona—Woodside 走廊（沿用我 Food System Atlas 项目的数据管线，113 个 census tract）。目标不是做一个“什么都能聊”的机器人，而是一个只基于已收录资料作答的助手：每条回答能追溯到文件章节或 GIS 要素；资料里没有的，明确说不知道。

系统与架构
  • 资料库：规划文件按章节分块入索引（保留文件名+章节，供引用）；4 个 GIS 图层（ACS 人口 / 311 投诉 / NYPD 报案 / 餐厅卫生检查）以 GEOID 对齐
  • 双路问答：文档类问题走检索（BM25 基线，零 Key 可复现）；排名、中位数、单 tract 画像、相关分析等数字类问题走结构化查询，由代码直接算图层属性
  • 拒答机制：检索分数与词覆盖双信号低于阈值即拒答，阈值用评估集中的无答案题校准
  • 界面：FastAPI 提供 /ask 接口；网页左侧 Leaflet 地图可切换四个指标图层，右侧问答面板展示答案与引用
关键决策
  • 数字不经模型：LLM 不负责算数。“哪个 tract 311 投诉最高”由结构化查询计算，引用到图层 + GEOID
  • 方法护栏写进系统：每千人比率排名默认只算人口 ≥2,000 的 tract——原始榜首是一个 344 人的 tract，比率被小分母放大，报它“问题最严重”是方法错误；这个理由同时写进回答本身
  • 不用微调：问题是“资料检索与引用”，不是“教模型新知识”，RAG 可解则不微调
  • 无 Key 演示模式明确标注：抽取式返回检索原文 + 引用，响应里标明模式，不伪装成生成结果
评估

先建尺子再调系统：测试集每题标注标准答案与应引来源，分五类——文档事实、GIS 排名/画像、跨源相关、无答案（应拒答）、口径陷阱。种子集 12 题结果：

  • Recall@5（应引来源命中）：1.00
  • 答案关键值命中率：1.00
  • 拒答准确率：1.00；过度拒答率：0.00

如实标注局限：题量小、自编题存在偏差，这组数字只证明流程与口径跑通。下一步扩到 40 题，并做 BM25 与向量检索的对照实验——同一把尺子，才比得出提升。

失败案例
  • 引用张冠李戴：311 排名的答案曾引用人口图层，而非产出该指标的 311 图层（字段来自合并属性表）。修复字段→图层映射后，评估 Recall 从 0.89 升到 1.00。教训：引用“存在”不等于引用“正确”，评估必须核来源归属
  • 小分母霸榜：见“关键决策”——已加人口门槛并把口径写进回答
  • 诚实的“不支持”：直觉上“西裔占比高的区域餐厅评级更差”，实测相关系数 r = 0.06，数据不支持。系统按数据回答，不顺着提问者的叙事编故事
结果与下一步

系统已在本地完整跑通：命令行演示、5 个核心行为测试、评估脚本、地图界面与 API 均验证可用。代码与数据清单公开在本站仓库：GitHub 查看代码 →

下一步：评估集扩至 40 题；接入向量检索做对照；接 LLM 生成模式（提示词已按“有引才答、无据拒答”写好，待 API Key）。

我的角色与复盘

独立完成：数据管线复用与整理、分块与检索、GIS 查询、拒答阈值、评估集与评估脚本、地图界面。复盘：这个项目让我确认了一件事——AI 产品的可信度不来自“回答得像人”，而来自引用可核、错误可测、边界可说清。这也是我接下来做每个 AI 功能都会先建评估集的原因。
